# Queueing review comments in the existing Codex agent

Research date: 2026-09-10. Installed versions checked without contacting the live server: Herdr 0.8.2 and codex-cli 0.153.4. Codex implementation claims below refer to the public `rust-v0.153.4` tag. No live prompts were sent and no private session transcripts were read.

## Conclusion

Use `codex queue --thread UUID --message TEXT` for the selected existing Codex agent. This command was missing from the initial investigation. In 0.153.4 it calls `thread/queue/add`, persists the message, and returns an authoritative queue-entry ID. A separately started embedded app server can enqueue for an unloaded target thread without resuming or executing that thread. The already-running TUI's owning server discovers the shared durable queue and runs its entries when idle. This corrects the earlier blanket claim that a new app server cannot queue into an existing TUI. Starting/resuming a second execution owner remains unnecessary. [CLI command](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/cli/src/queue_cmd.rs), [command implementation](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/session_queue_commands.rs), [queue service](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/ext/queue/src/service.rs).

| Transport | Native queue | Receipt | Existing running agent |
| --- | --- | --- | --- |
| `codex queue` | Yes, shared durable queue | Native queued-submission ID in success output | Existing owner consumes, provided storage and thread identity match |
| Queue-only stdio app server | Same durable queue | Structured queue ID and caller-selected client message ID | Existing owner consumes; no resume/start request needed |
| Existing owning app server connection | Yes | Structured IDs plus owner turn events | Directly reaches owner |
| TUI paste then Tab | Yes under expected composer state | No authoritative acceptance receipt | Composer/modal/draft interference possible |
| `codex exec` or another resumed execution | Separate execution | Unrelated to queue insertion | Not needed for this integration |

Native queue acceptance is distinct from completed execution. Retain the receipt and bind the eventual final reply to the actual matching input and turn; never take the next ambient assistant reply.

## Durable queue and transport details

The queue extension polls SQLite's change version every 10 seconds, queries revisions for loaded threads, emits queue-change notifications, and wakes idle threads. Local enqueue also wakes a target if it is loaded in that process. Idle lifecycle handling starts one queued input and removes its record after successful turn start. Busy threads wait until idle. Interrupted threads are deliberately not woken; pending messages can therefore remain pending indefinitely. The regression test `externally_changed_queues_dispatch_independently_and_retry_failed_wakes` uses a separate SQLite runtime to enqueue for the active owner, explicitly testing cross-process-style writes. [Extension registration](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/ext/queue/src/lib.rs), [watcher and dispatch](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/ext/queue/src/service.rs), [regression tests](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/ext/queue/tests/queue_service.rs).

This requires a local persistent thread store and an available state database. In-memory stores have no queue backend. Queue add can read an unloaded target's metadata without its history, but rejects archived targets, loaded ephemeral targets, and unloaded spawned subagents. The target owner must include this queue extension; checking only the reviewer's `codex --version` does not prove that an older already-running process supports it. [Queue initialization](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/app-server/src/message_processor.rs), [target validation](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/app-server/src/request_processors/thread_queue_processor.rs).

Preserve the target's executable/version, `CODEX_HOME`, configuration/profile/overrides, working-directory-dependent configuration, and resolved SQLite state location (`sqlite_home` can differ from `CODEX_HOME`). The queue backend is process-scoped: later configuration reloads do not move it. A new sender accidentally opening a different database can acknowledge a queue the current owner will never consume. Use the exact thread UUID, not a possibly ambiguous session name. [Process-scoped storage](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/app-server/src/message_processor.rs), [SQLite initialization](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/app-server/src/lib.rs).

The CLI can connect to an explicit remote endpoint or auto-reuse a compatible default local daemon. Configuration overrides, workload identity, or other launch conditions can prevent implicit daemon reuse. If an embedded sender would bypass an existing default daemon, `codex queue` rejects it and asks for corrected overrides or explicit `--remote`; unsupported daemon queue APIs also produce an error. Preserve these errors rather than falling back to pane injection or resuming the thread. [Launch selection](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/session_archive_commands.rs), [queue-specific safeguards](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/session_queue_commands.rs), [CLI tests](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/cli/tests/queue.rs).

The CLI accepts message text as an argument, without a stdin/file option in this version, and prints `Queued message {id} for thread {uuid}.` It generates its own client user-message UUID and does not expose that UUID separately. Persist the returned native queue ID and a unique marker inside the submitted input for later attribution. An ambiguous timeout/crash after sending must not trigger blind resubmission: the message may already be queued. [Arguments](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/cli/src/queue_cmd.rs), [receipt](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/session_queue_commands.rs).

For large prompts or structured receipts, a queue-only `codex app-server --listen stdio://` client can send JSONL over stdin: initialize with `capabilities.experimentalApi: true`, send the initialized notification, then `thread/queue/add` with `threadId`, `clientUserMessageId`, and text input. Wait for the matching response before clean shutdown. This reaches the same durable service and avoids OS command-argument limits; protocol/input limits still apply. Never call `thread/resume`, `turn/start`, or `thread/queue/start` merely to enqueue. This direct transport does not inherit `codex queue`'s daemon-selection safety checks: storage/owner routing must be established explicitly. The queue response supplies acceptance, not another owner's future live events. [App-server transport and initialization](https://developers.openai.com/codex/app-server), [shared queue processor](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/app-server/src/request_processors/thread_queue_processor.rs).

## Herdr transport

The current repository's `HerdrClient::prompt_agent` sends `agent.prompt {target,text}` and returns unit. Herdr documents that this writes text and encoded Enter, including bracketed-paste handling. Its wait follows agent lifecycle state, not a distinct submitted turn; an already running turn can satisfy completion. It cannot identify which comment produced an answer. [Herdr automation](https://herdr.dev/docs/agent-automation/), [socket API](https://herdr.dev/docs/socket-api/).

The installed `herdr api schema --json` exposes `pane.send_text {pane_id,text}`, `pane.send_keys {pane_id,keys}`, and `pane.send_input {pane_id,text?,keys?}`. The repository already wraps the first two. A candidate single-request terminal sequence is bracketed-paste start (`ESC [ 200 ~`), one complete marked comment prompt, bracketed-paste end (`ESC [ 201 ~`), then Tab. The schema permits that string, but does not itself prove the installed server passes those bytes unchanged; validate exact byte handling against an isolated pane before choosing it. Likewise, verify ordering and any implicit paste wrapping before relying on `pane.send_input` with text plus `keys:["tab"]`. Do not wrap a payload twice.

One request prevents gaps between the reviewer's own paste/key calls. It does not provide atomic composer ownership or protect against a pre-existing draft, remapped keys, an approval dialog, a popup, a changed pane occupant, or concurrent human input. Neither Herdr's input schema nor the inspected Codex protocol supplies an authoritative read-only composer-empty check or compare-and-swap submission. Screen reads may help diagnose but cannot guarantee this precondition.

For ordinary text, the TUI's queue key invokes submission with queuing enabled when working, and immediate submission when idle. Each plain queued item is popped and the drain loop stops before the next one. There is no need to send a special first Enter and wait for busy status. Recovered queues and other suppression conditions can stop automatic draining; queueing is not a guarantee of eventual completion. [Composer queue keys](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/bottom_pane/chat_composer.rs#L3560), [queue drain](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/chatwidget/input_flow.rs#L140).

Explicit bracketed paste supports large inputs through stored placeholders and clears heuristic paste-burst suppression. It inserts at the current composer position; an existing draft remains. In Vim query mode it inserts into the query editor instead. Begin prompts with ordinary text rather than slash-command or bang-shell syntax, and encode/reject embedded terminal control sequences before terminal injection. Large-paste support does not solve modal state or draft safety. [Paste implementation](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/bottom_pane/chat_composer.rs#L1217).

## Structured native queue API

The installed CLI's `codex app-server generate-json-schema --experimental` exposes these experimental requests: `thread/queue/add`, `thread/queue/list`, `thread/queue/update`, `thread/queue/delete`, `thread/queue/reorder`, and `thread/queue/start`, with `thread/queue/changed` notifications. `add` requires `threadId`, `clientUserMessageId`, and structured `input`; it returns a queued submission with `id`, `clientUserMessageId`, and `input`. `start` accepts `threadId` and optional `queuedSubmissionId` and returns a `Turn`. The implementation requires a loaded thread before starting. These are version-specific experimental interfaces, not a stability promise. Their availability alone does not establish automatic draining for every standalone server configuration. [Queue processor](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/app-server/src/request_processors/thread_queue_processor.rs).

A connection to the existing owner is preferable when live structured turn events are needed; queue-only submission does not require that connection. Subscribe before submission; retain the native queued submission ID and the reviewer's unique `clientUserMessageId`. Use actual returned/observed turn IDs for completion, with the queue-to-user-message identity as the bridge. `turn/steer` modifies an active turn. Do not assume `turn/start` always creates a separate turn: the installed experimental schema describes cases where it steers an already active turn. [App-server documentation](https://developers.openai.com/codex/app-server).

A normal embedded TUI can use `AppServerClient::InProcess`; there is no implied public socket to discover from its thread ID. An explicit remote TUI/app-server deployment is a different topology. Starting another app server and resuming the same disk history does not attach to that in-process owner and must not be used as a substitute. Herdr's process/session metadata can identify a target but does not prove an owning RPC endpoint. [Embedded transport check](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/tui/src/app_server_session.rs#L487).

## Capturing only the corresponding final reply

For a connected owning app server, `item/completed` carries `threadId`, `turnId`, and an item. Agent message items include text and optional phase (`commentary` or `final_answer`). `turn/completed` provides the terminal turn status and error. Buffer final output per identified turn, append only after successful completion, and never use commentary or a response from a different turn. Interrupted/failed turns must remain explicitly unsuccessful rather than borrowing a subsequent successful answer. [App-server events](https://developers.openai.com/codex/app-server).

For terminal injection, rollout observation is a version-coupled fallback. Give each submission an opaque unique marker and persist its mapping to the comment before injecting. Watch only the selected agent's exact Codex session, starting from a known file offset/baseline. Bind the marker in the actual user input to that input's turn ID; then accept only that turn's terminal final answer. A marker echoed by an assistant is not evidence of input acceptance. Multiple comment markers in one submitted input make one-to-one attribution ambiguous and should fail closed.

Relevant 0.153.4 rollout records are JSONL envelopes with `timestamp`, optional `ordinal`, `type`, and `payload`. Event messages are nested under outer `type:"event_msg"`:

| Event payload type | Relevant fields | Use |
| --- | --- | --- |
| `task_started` (alias `turn_started`) | `turn_id` | Establish actual turn identity |
| `user_message` in legacy history | `message`, optional `client_id` | Find the submitted marker |
| `item_completed` in paginated history | Typed completed turn item | Read the actual user input/final message with its available turn identity |
| `agent_message` in legacy history | `message`, optional `phase` | Candidate final text only; not completion by itself |
| `task_complete` (alias `turn_complete`) | `turn_id`, optional `last_agent_message`, optional `error` | Authoritative completed-turn last message for that ID |
| `turn_aborted` | optional `turn_id`, `reason` | Reject/mark interrupted; never append a later ambient reply |

`turn_context` records also have optional `turn_id`. The safest successful extraction is the matching `task_complete.turn_id` with no error and a present `last_agent_message`; missing IDs or missing final text are unresolved, not permission to guess. Preserve state across partial JSONL writes, duplicate/replayed records, reconnects, and app restarts, and deduplicate completion by submission plus turn ID. [Protocol event definitions](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/protocol/src/protocol.rs), [rollout envelope](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/history/src/lib.rs#L223).

A parser supporting only `user_message`/`agent_message` is insufficient: legacy history persists those while paginated history persists `item_completed` instead. Turn start, completion, and abort events persist in both. Queue-change notifications are transient, so a rollout tail cannot acknowledge acceptance while a message is still waiting in the native queue. Validate representative synthetic fixtures for both history modes and fail on unknown modes rather than silently dropping correspondence. [Persistence policy](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/rollout/src/policy.rs).

Resolve the selected agent's session from Herdr's `agent_session` identity, not by selecting the newest file in the repository. Use the owning process's `CODEX_HOME`, which overrides the default `~/.codex`; the reviewer's environment can differ. Active rollouts live under `sessions`, with archived sessions under `archived_sessions`. Verify the first `session_meta` identity. Do not hardcode one filename: revert can retain the thread ID while changing the rollout ID, and compression/history migration exists. Unsupported discovery should produce an actionable unavailable state. [Codex home resolution](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/utils/home-dir/src/lib.rs), [session roots](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/rollout/src/lib.rs#L68), [recorder and revert naming](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/rollout/src/recorder.rs#L98).

## Repository implications and validation boundary

The current `review-guide-runner` uses a response-file mailbox and `prompt_agent`; it has no existing native Codex session/rollout reader to reuse. Native queuing requires a new submission path and explicit submission/turn tracking. Mark native acceptance from the queue receipt, then track the actual matching turn; append exactly one corresponding final response; expose aborted, failed, ambiguous, or missing-session states without reassigning another answer. Do not require Codex to edit the comment file or write a reply mailbox merely to obtain its final reply.

Before implementation is accepted, isolated tests should cover idle and busy native queue submissions, two queued comments producing distinct turns, an unrelated in-progress turn finishing first, unrelated human messages, final versus commentary, interruption/error, duplicate and partial records, paginated and legacy history, process/session replacement, and a pre-existing draft or modal composer. Prefer the durable queue path over the terminal fallback. This investigation verified documentation, schemas, and public source only. It did not demonstrate a live TUI round trip or guarantee safe composer injection under arbitrary UI state.
