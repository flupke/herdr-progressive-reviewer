What may Jev safely skip?

We tested whether a narrow category query and a conservative probability gate can identify review material the reviewer considers uninteresting, while leaving everything else for a human.

1. Define the target before tuning

LABEL AUDIT

Two labels were wrong

Two #[serde(default)] additions were first called insignificant. They change which saved records deserialize successfully, so their changed lines are now significant. These post-audit cases were kept out of tuning.

REVIEWER POLICY

“Interesting” is a scope decision

The reviewer wants to skip comment-only, import/re-export/module-only, formatting-only, test-only, prose-doc-only, generated-output-only and lockfile-only changes. A mixed hunk stays in review. Hand-written config and manifests remain in scope.

SAFETY RULE

Uncertain means required

An exclusion requires strong evidence that every target edit is in a skipped category. A fitting but uncertain hunk may be split at most twice without overlap; any unresolved part remains reviewable. That uncertainty split is proposed, not yet tested.

An import or module declaration can alter runtime behavior. The reviewer explicitly chose to exclude these lines anyway. The experiment measures agreement with that review policy, not semantic inertness.

2. Keep the unit meaningful and bounded

INPUT

A full diff hunk first

The opt-in Rust evaluator makes the hunk the initial target. It includes path, Rust hint, old/new rows, and an omission note. Context rows are marked separately from rows being judged.

SIZE

Estimate tokens, not bytes

The planner tokenizes the serialized request with o200k_base and uses a 14,000 estimated-token ceiling. Jev reported at most 15,083 actual input tokens in this run, under its 32k limit.

SPLIT

Recursive, without overlap

If a hunk does not fit, cut near half its estimated tokens at a legal boundary and repeat. Old/new replacements stay paired. An indivisible oversized piece stays required for human review.

plan(hunk):
    if token_count(serialized_request(hunk)) ≤ 14,000: send(hunk)
    else if legal midpoint exists:
        plan(left_half); plan(right_half)
    else: keep_for_human_review(hunk)

3. Compare questions on the same chunks

Each prompt saw the same 17 frozen candidates three times. A candidate is safe to exclude only if every target changed line is outside review scope. The category request batches three independent yes/no questions in one Jev call; each answer is its yes probability, with no separate confidence field.

Show the scope-aware Choice prompt
Classify only the changed target lines, using unchanged lines to understand them. The reviewer excludes whole blocks consisting only of comments, imports, use/re-export or module declarations, formatting, test-only code, prose docs, generated output, or lockfile changes. These categories are excluded even if an import or test can change behavior. If any target edit is outside those categories, choose significant, including a changed return value, serialized-data contract, runtime text, or review rule. For a mixed block choose significant. If category membership is unclear, choose uncertain. Judge ONLY rows with target=true; all other rows are context, even if added or deleted. Old changed lines were deleted; new changed lines were added.

Criteria:
significant — At least one target edit is outside the reviewer's excluded categories.
insignificant — Every target edit belongs to an excluded category, including behavior-changing imports.
uncertain — The supplied source cannot establish the category of every target edit.
Show the three category yes/no questions
is_comment_diff: Are ALL edits in rows with target=true exclusively comments or documentation, with no executable, attribute, or declaration edit?
is_import_diff: Are ALL edits in rows with target=true exclusively import statements, use or pub use re-exports, or mod/pub mod declarations? Include changed import targets and aliases.
is_formatting_diff: Are ALL edits in rows with target=true exclusively formatting or syntactic presentation that preserves the same executable behavior, data contract, and user-facing text?

All three: Other rows are context, even if changed.
Show the current production query used as baseline
Decide whether THIS exact changed block needs its own explanation in a code review. It treats explanatory comments, formatting and routine annotations as potentially insignificant, while listing behavior, contracts, dependencies and meaningful imports as significant. For split windows, only target=true rows count. The full exact baseline request is preserved in the run log.

5. What the result supports

OBSERVED

0.90 worked on this set

Both revised queries excluded all 12 development and all 6 holdout negative judgments, with zero false exclusions among 33 positive judgments. The old query missed six negative judgments, including the behavior-changing import that the reviewer chose to skip.

BOUNDARY

This is not a safety guarantee

Fixtures and labels were agent-authored; three repeats and related old/new lines are correlated. Test-only edits, docs, generated output and lockfiles lack dedicated examples. The proposed uncertainty split was not evaluated.

NEXT

Keep production unchanged

The trial suggests a 0.90 category gate is worth a larger independently labelled evaluation. It does not justify silently switching production exclusion behavior yet.
